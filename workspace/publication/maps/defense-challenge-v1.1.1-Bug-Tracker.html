01BLOCKERVERIFIED

Arena reset can remove ticking areas from a newly started run

BUG-DEF-LEASE-RESET
View Details ↓Collapse Details ↑
Issue
The same arena can restart before its prior async reset finishes, allowing old cleanup to remove ticking areas from the new match and break simulation.
How to Reproduce
  1. Start a Defense match in an arena.
  2. End or reset the match so the arena begins its map reset.
  3. Start a new match in the same arena before reset work finishes.
  4. Confirm the new match loses its arena ticking areas and gameplay simulation can stop.
Observed
A new run can reuse the arena before reset finishes, then the old reset releases the ticking-area lease used by the new run.
Expected
An arena becomes reusable only after reset completes, and old cleanup cannot release resources owned by a newer run.
Resolution
Keep the arena unavailable until reset completes, or generation-bind ticking-area lease release so old cleanup cannot release a newer run's lease.
Technical Analysis
Arena/session cleanup exposes the arena as reusable before asynchronous reset completion. The next run can reuse the existing ticking-area lease, while the previous run's delayed cleanup still owns a release path and removes that lease underneath the new run.
Source Context
behavior_packs/BP/scripts/chunks/chunk-ZDK4WOHG.js — Owns Defense arena reset, session reuse, and ticking-area lease lifecycle.
Must Preserve
  • Existing arena queue and concurrency policy must keep working.
  • Cleanup from one arena must not affect another active arena.

02BLOCKERVERIFIED

Delayed wave can clear before failed spawn retries finish

BUG-DEF-WAVE-RETRY
View Details ↓Collapse Details ↑
Issue
A delayed enemy group can be counted as cleared when its first spawn attempt fails, letting the wave advance before the queued retry spawns its enemies.
How to Reproduce
  1. Reach Defense Level 15, Wave 3.
  2. Trigger the delayed enemy group while its spawn chunk is not ready.
  3. Let the first spawn attempt fail and queue its retry.
  4. Confirm the wave can advance as cleared before the delayed enemies actually spawn.
Observed
Pending group count can reach zero with no live hostiles, so wave-clear logic can run before retry-spawned enemies appear.
Expected
A wave remains active while any required enemy spawn is still pending retry.
Resolution
Keep delayed groups pending until spawn retries resolve, and block wave-clear reconciliation while required enemy spawns remain outstanding.
Technical Analysis
WaveScheduler removes the delayed group from pending accounting immediately after the first spawn attempt, while EntityLoader may still own retries. Hostile-clearance reconciliation then sees zero live tagged enemies and can complete the wave even though required spawns remain outstanding.
Source Context
behavior_packs/BP/scripts/chunks/chunk-ZDK4WOHG.js — Contains delayed wave scheduling, spawn retry ownership, hostile accounting, and wave-clear reconciliation.
Must Preserve
  • Normal successful spawn groups must keep their current wave timing.
  • Retry logic must remain bounded and arena-scoped.

03MAJORVERIFIED

Reconnect during preload can carry stale inventory into a new match

BUG-DEF-PRELOAD-INVENTORY
View Details ↓Collapse Details ↑
Issue
A player who disconnects before the fresh-session inventory wipe can reconnect after it and keep ordinary stale items into the new Defense session.
How to Reproduce
  1. Carry a recognizable non-session item in an inventory slot.
  2. Start a Defense match, then disconnect before the preload inventory wipe runs.
  3. Reconnect after the wipe while the session is still preloading.
  4. Confirm the stale item remains when the new match reaches buy or gameplay phase.
Observed
The preload wipe only affects online players, and reconnect plus later loadout refresh does not clear ordinary items outside managed loadout state.
Expected
Every player entering a fresh Defense session passes the same full inventory reset regardless of reconnect timing.
Resolution
Record the fresh-session inventory reset per player and enforce the missed full clear on reconnect before buy or gameplay continuation.
Technical Analysis
The fresh-session wipe is implemented as a batch action over players online at one preload tick rather than a per-player session invariant. Reconnect during preload does not reconcile the missed full clear, and later loadout refresh uses a partial managed-item cleanup.
Source Context
behavior_packs/BP/scripts/chunks/chunk-ZDK4WOHG.js — Owns preload inventory clearing, reconnect handling, and later loadout application.
Must Preserve
  • Mid-session loadout refresh must not erase unrelated state unless the fresh-session boundary requires it.

04MAJORVERIFIED

Reconnect bypasses an active combat respawn countdown

BUG-DEF-RESPAWN-RECONNECT
View Details ↓Collapse Details ↑
Issue
A player can disconnect during the death countdown and reconnect back into active gameplay before the intended respawn delay finishes.
How to Reproduce
  1. Start a Defense match and die during active combat.
  2. Disconnect while the respawn countdown is still running.
  3. Reconnect before the countdown expires.
  4. Confirm the player returns to active gameplay before the original respawn delay finishes.
Observed
Combat recovery restores spectator state, then a second reconnect path restores survival, loadout, and gameplay position about five ticks later.
Expected
A reconnecting player with a pending respawn stays in spectator/death state until the existing countdown ends.
Resolution
Guard active-session reconnect recovery with the existing pending-respawn state so CombatTracker remains the sole owner until the death timer resolves.
Technical Analysis
CombatTracker owns pending respawn state and correctly restores spectator/countdown on reconnect. GameManager independently handles the same reconnect and later restores active gameplay without consulting that pending-respawn owner.
Source Context
behavior_packs/BP/scripts/chunks/chunk-ZDK4WOHG.js — Contains CombatTracker pending respawn handling and GameManager reconnect recovery.
Must Preserve
  • Normal reconnect outside a death countdown must still restore the active session.
  • Existing respawn timing must remain unchanged.

05MAJORVERIFIED

Six playable arenas expose only two concurrent sessions

DM-DEF-ARENA-CAPACITY
View Details ↓Collapse Details ↑
Issue
Defense presents six playable arena surfaces, but only two can run at once; additional ready groups must queue despite having their own arena.
How to Reproduce
  1. Prepare valid parties in 3 different Defense arenas.
  2. Start the first 2 arenas so both hold active arena leases.
  3. Ready and start the third arena.
  4. Confirm the third group is queued even though its own visible arena is otherwise available.
Observed
Six arenas accept parties, but MAX_CONCURRENT_ARENAS limits active ticking-area leases to two and queues later sessions.
Expected
Presented independent arena capacity matches delivered concurrency, or the lower limit is explicitly authored as the player-facing capability.
Resolution
Use a proven residency strategy that supports the presented arena concurrency, or change the authored player-facing capacity to match the actual supported limit.
Technical Analysis
Defense exposes six arena/join surfaces, while runtime admission allows only two held arena leases. Each active arena uses three residency regions. Queueing explains the implementation constraint but does not erase the delivered-capacity mismatch.
Source Context
behavior_packs/BP/scripts/chunks/chunk-ZDK4WOHG.js — Owns Defense arena configuration, two-lease concurrency policy, residency resources, and queue admission.
Must Preserve
  • Per-arena simulation coverage and isolation must remain correct.
