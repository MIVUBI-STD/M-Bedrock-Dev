01MAJORVERIFIED

Main-lobby players can remain in Creative mode after spawn

BUG-BAD-LOBBY-CREATIVE-SPAWN
View Details ↓Collapse Details ↑
Issue
The selected world defaults players to Creative, while the canonical main-lobby entry path teleports and clears inventory without normalizing gamemode or player abilities. Tester runtime confirms first-spawn players remain Creative. The role system otherwise consistently uses Adventure for lobby/staging/guessers and grants Creative only to the active builder.
How to Reproduce
  1. Join Build & Decode v1.1.1 as a normal non-admin player with a fresh/first spawn.
  2. Allow the normal welcome/main-lobby flow to complete.
  3. Check the player's gamemode.
  4. Confirm the player remains in Creative instead of being normalized to the lobby Adventure role.
Observed
The current artifact has world GameType=Creative and ForceGameType disabled. ArenaService.enterMainLobby() teleports and clears the player but does not set Adventure, disable mayfly, or restore mute state. WelcomeManager also does not normalize gamemode. AntiCheatManager contains corrective logic but is not registered by production main.js.
Expected
Normal players in the main lobby and non-builder roles are Adventure with normal lobby abilities; Creative is granted only by the active builder role or an explicitly authorized maintenance role.
Resolution
Make the existing main-lobby entry/recovery owner normalize the complete lobby player state: set Adventure, disable mayfly, restore mute/managed abilities, then clear inventory/equipment and teleport. Continue granting Creative only from the active builder-role owner. Also set the world default gamemode consistently as defense in depth, but do not rely on the world default as the sole fix.
Technical Analysis
This is a role-state ownership gap, not only a world-default setting. The selected artifact repeatedly establishes Adventure as the safe non-builder state, but enterMainLobby does not enforce that state. Relying only on changing the world default would still leave stale returning-player state possible.
Source Context
behavior_packs/Build_Decode_BP/scripts/modules/arena/ArenaService.js
enterMainLobby() clears inventory and teleports to HUB without normalizing gamemode/mayfly/mute; other recovery/staging paths explicitly set Adventure and disable mayfly.
behavior_packs/Build_Decode_BP/scripts/modules/welcome/WelcomeManager.js
First-spawn welcome processing eventually routes the player to enterMainLobby but does not enforce player role state itself.
behavior_packs/Build_Decode_BP/scripts/main.js
Production bootstrap does not register AntiCheatManager.
behavior_packs/Build_Decode_BP/scripts/modules/anticheat/AntiCheatManager.js
Contains non-admin Creative/Spectator correction logic but is inactive in the production bootstrap.
Must Preserve
  • Active builders must still receive Creative during their building round.
  • Guessers and staging players remain Adventure.
  • Authorized maintenance/admin workflows must keep their explicitly intended privileges.
  • Reconnect and match recovery remain owned by the existing session lifecycle.

DESIGN MISMATCH 1

02MINORVERIFIED

Authored final-standings presentation is not used at match completion

BUG-BAD-FINAL-RESULT-PRESENTATION
View Details ↓Collapse Details ↑
Issue
The artifact contains a dedicated final-standings UI explicitly authored for the end of a game, but the terminal match flow never invokes it. Runtime testing observes the match ending and returning to the lobby without a dedicated victory/result presentation such as the authored standings surface, title, or victory sound.
How to Reproduce
  1. Complete a normal Build & Decode match in v1.1.1.
  2. Observe the completed result is committed and a chat summary may be sent.
  3. Confirm the authored final standings UI is never displayed.
  4. Observe players are reset/returned to the lobby without a dedicated final victory/result presentation.
Observed
GuessTheBuildUI.showFinalStandings() is implemented and documented as the end-of-game standings presentation, but no production caller invokes it. ArenaService.finish() commits the result, sends matchSummary() only as chat text, and immediately proceeds into resetArena().
Expected
The authored end-of-match presentation is reachable from the completed-match flow so players receive a clear terminal result before the arena resets and returns them to the lobby.
Resolution
Route completed matches through the existing final-result presentation owner after durable result settlement and before arena reset. Extend that same UI/presentation owner to handle team Win/Draw semantics and, if desired, add the requested victory title/sound there. Keep one result authority; presentation must consume the already-settled result rather than recalculate winners.
Technical Analysis
This is stronger than a general UX preference because the selected artifact itself contains a dedicated showFinalStandings() capability with an explicit end-of-game purpose, yet the playable terminal flow does not route to it.
Source Context
behavior_packs/Build_Decode_BP/scripts/modules/guessthebuild/GuessTheBuildUI.js
Defines showFinalStandings() with the documented purpose 'Show final standings at end of game'.
behavior_packs/Build_Decode_BP/scripts/modules/arena/ArenaService.js
finish() settles the result, sends a chat summary, then immediately calls resetArena() without invoking the authored final standings UI.
Must Preserve
  • Exact-once result settlement and leaderboard persistence.
  • Correct team Win/Draw semantics from the canonical result.
  • Automatic cleanup and return to lobby after the presentation window.
