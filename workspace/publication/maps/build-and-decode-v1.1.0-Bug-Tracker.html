01MAJORVERIFIED

Creative-built entities can survive plot reset into later rounds

BUG-BAD-CREATIVE-ENTITY-RESIDUE
View Details ↓Collapse Details ↑
Issue
The active builder is intentionally placed in Creative and can construct vanilla block-created entities such as an Iron Golem inside the plot. Plot cleanup resets blocks with fill air and removes only a narrow tagged transient allowlist (items, XP orbs and selected projectiles). Non-transient player-created entities are not part of the cleanup footprint, so they can survive round reset and arena reuse.
How to Reproduce
  1. Enter an active round as the builder in Creative mode.
  2. Inside the active build plot, place four iron blocks in a T shape and add a carved pumpkin to create an Iron Golem.
  3. Allow the round to end and the normal plot reset to run.
  4. Start the next round or reuse the same arena.
  5. Confirm the plot blocks are reset but the created Iron Golem can remain because it is outside the cleanup entity allowlist.
Observed
The builder can create an Iron Golem from ordinary Creative blocks. The reset removes the construction blocks but the entity is not matched by the cleanup allowlist and therefore can remain in the arena after the round.
Expected
All gameplay-significant mutations that an ordinary builder can create inside the authored plot must either be prevented or included in the arena reset baseline before the next round/session becomes active.
Resolution
Make reset ownership match the complete builder capability surface. Prefer removing/cleaning all non-authored entities inside the current arena/plot generation, or explicitly prevent vanilla entity-construction patterns if those entities are not part of gameplay. Keep cleanup arena- and generation-scoped.
Technical Analysis
ArenaService gives the builder Creative mode and protects specific dangerous items, including spawn eggs, but ordinary iron blocks and carved pumpkin remain valid build materials. The cleanup path resets plot blocks and only removes arena/match-tagged minecraft:item, minecraft:xp_orb, minecraft:arrow, minecraft:snowball and minecraft:egg entities. Player-created persistent entities such as minecraft:iron_golem are not included, so the mutation footprint is larger than the reset footprint.
Source Context
behavior_packs/Build_Decode_BP/scripts/modules/arena/ArenaService.js — Builder role enters Creative mode; clean/reset logic clears plot blocks but only removes a narrow transient entity allowlist.
behavior_packs/Build_Decode_BP/scripts/modules/guessthebuild/GuessTheBuildManager.js — Round setup/role flow authorizes the active builder to construct inside the plot before cleanup.
Must Preserve
  • Normal Creative building with allowed blocks.
  • Arena isolation between the four replicas.
  • Authored map entities and presentation entities outside the reset ownership scope.
  • Generation-token protection against stale cleanup.

02MAJORVERIFIED

A fully departed team can remain eligible to win the match

BUG-BAD-DEPARTED-TEAM-WINNER
View Details ↓Collapse Details ↑
Issue
After a match has started, Exit to Lobby and offline-expiry remove players from the active members roster but preserve their player/team records for resumability/history. Final team standings are then built from all historical state.players records rather than the active/eligible members roster. In a match with three or more teams, one team can fully leave after scoring, the remaining teams can continue, and the departed team can still be declared the winner and persisted into leaderboard results.
How to Reproduce
  1. Start a team match with at least three active teams.
  2. Let Team A obtain the highest score.
  3. Have every Team A player use Exit to Lobby, or allow them to expire after disconnect, while at least two other teams remain active.
  4. Allow the remaining teams to complete the match without surpassing Team A's score.
  5. Observe that Team A remains in final standings and can be declared/persisted as the winner even though it has no active members.
Observed
depart()/expire() remove players from state.members but leave state.players/playerTeams after the match has started. teamStandings() enumerates Object.keys(state.players), and resultFields() derives winnerTeamIds/winnerIds from that historical roster.
Expected
A team with no active eligible members after explicit exit or expiry must not remain eligible for the final winner set. Historical contribution may be retained for audit/statistics only if it is explicitly separated from final winner eligibility.
Resolution
Separate historical participant/contribution records from final-result eligibility. Derive winner-eligible teams from the authoritative active/eligible roster at terminal commit, while preserving historical score data only according to the intended forfeit policy.
Technical Analysis
Active-session continuation correctly uses state.members and requires at least two active teams, but final-result eligibility switches ownership to the historical state.players ledger. TeamRules.teamStandings(state) explicitly calls activeTeamIds(state, Object.keys(state.players)) and also derives each team's member list from Object.keys(state.players). GuessTheBuildManager.resultFields() then builds winner IDs from those standings, and MatchResults persists them. The contradiction is deterministic from source.
Source Context
behavior_packs/Build_Decode_BP/scripts/modules/arena/ArenaService.js — depart() removes the player from state.members but, after the match has started, intentionally retains state.players/playerTeams.
behavior_packs/Build_Decode_BP/scripts/modules/arena/ArenaSessions.js — expire() removes expired players from state.members but retains their historical player/team records while allowing play to continue if two active teams remain.
behavior_packs/Build_Decode_BP/scripts/modules/arena/TeamRules.js — teamStandings() derives final teams and members from Object.keys(state.players), not the active eligible state.members roster.
behavior_packs/Build_Decode_BP/scripts/modules/guessthebuild/GuessTheBuildManager.js — resultFields() derives winnerTeamIds and winnerIds directly from teamStandings().
behavior_packs/Build_Decode_BP/scripts/modules/arena/MatchResults.js — Completed results persist the derived winner IDs and lifetime stats.
Must Preserve
  • Reconnect/resumability history for temporarily offline players.
  • Previously earned contribution data according to the intended forfeit policy.
  • Minimum-two-active-team continuation behavior.
  • Exact-once result persistence and leaderboard accounting.

03MAJORVERIFIED

Drawn teams are persisted as Wins

BUG-BAD-DRAW-WIN-COUNTER
View Details ↓Collapse Details ↑
Issue
The match UI explicitly classifies equal top scores as a Draw, but resultFields() places every tied leading team into winnerTeamIds/winnerIds. MatchResults then increments each tied player's persistent wins counter. That wins field is displayed to players and is also used as a global leaderboard tie-breaker.
How to Reproduce
  1. Start a normal team match with at least two teams.
  2. Finish the match with two or more teams tied for the highest score.
  3. Confirm the match summary/result UI displays Draw.
  4. Open the leaderboard/personal stats after the result is committed.
  5. Confirm players on every tied top team received an additional Win.
Observed
The result presentation says Draw while all tied leading teams are written as winners and each tied player gains +1 Win. Persistent Wins can then affect leaderboard ordering.
Expected
A Draw should preserve the draw result and completed-match/score accounting without incrementing the persistent Win counter for every tied team, unless the product intentionally defines a draw as a win everywhere.
Resolution
Represent terminal outcome semantics explicitly: when multiple top teams tie, persist a draw with no winner IDs (or a separate tiedTeamIds field) and do not increment wins. Keep total score and games played accounting unchanged.
Technical Analysis
GuessTheBuildManager.matchSummary() uses the explicit Draw presentation whenever multiple teams share the top score. The same manager's resultFields() nevertheless classifies all top-scoring teams as winnerTeamIds and all of their members as winnerIds. MatchResults._apply() increments wins for any player in winnerIds. LeaderboardService then sorts equal totalScore entries by wins, so the semantic mismatch can alter persistent ranking.
Source Context
behavior_packs/Build_Decode_BP/scripts/modules/guessthebuild/GuessTheBuildManager.js — Displays Draw for multiple leaders but also returns every tied leader as a winner.
behavior_packs/Build_Decode_BP/scripts/modules/arena/MatchResults.js — Increments persistent wins for every player in winnerIds on completed matches.
behavior_packs/Build_Decode_BP/scripts/modules/leaderboard/LeaderboardService.js — Exposes wins and uses wins as the second global ranking sort key after totalScore.
behavior_packs/Build_Decode_BP/scripts/modules/leaderboard/LeaderboardMenus.js — Player-facing result and personal-stat surfaces distinguish Draw from Wins.
Must Preserve
  • Player-facing Draw presentation.
  • Total score and games-played accounting.
  • Exact-once match result journal.
  • Leaderboard deterministic ordering.

04MAJORVERIFIED

Creative equipment can persist across role changes, exit and replay

BUG-BAD-EQUIPMENT-ROLE-LEAK
View Details ↓Collapse Details ↑
Issue
The builder is placed in Creative mode, but the canonical player reset helper clears only the inventory container. It never clears the separate equippable slots such as armor/offhand. A builder can therefore equip Creative-obtained gear and carry it into a later Adventure guesser role, lobby state, reconnect recovery or subsequent session.
How to Reproduce
  1. Enter an active round as the builder in Creative mode.
  2. Equip a Creative-obtained armor/chest/offhand item, for example an Elytra or shield.
  3. Finish the round so the player becomes a guesser, or use Exit to Lobby and then join another session.
  4. Observe the normal inventory cleanup/role transition.
  5. Confirm the equipped item is not owned by clearInventory() and can remain equipped across the transition.
Observed
clearInventory() removes inventory container slots only. No gameplay cleanup path clears minecraft:equippable slots, while builder Creative access allows equipment acquisition and use.
Expected
Role/session cleanup must restore the complete managed player state, including equipment/offhand acquired during Creative builder access, before the player becomes a guesser, returns to lobby or starts another session.
Resolution
Extend the canonical player-state reset owner to clear managed equipment/offhand slots through the equippable component in addition to the inventory container. Keep one reset helper rather than adding role-specific cleanup paths.
Technical Analysis
ArenaService.clearInventory() only accesses the minecraft:inventory component container and clears its slots. Repository-wide gameplay paths do not clear minecraft:equippable equipment slots. Because the authored builder role grants ordinary Creative catalog access, equipment state is a reachable mutable resource and must be part of reset/recovery ownership.
Source Context
behavior_packs/Build_Decode_BP/scripts/modules/arena/ArenaService.js — Defines clearInventory() using only minecraft:inventory and invokes it for role setup, departure and recovery transitions.
behavior_packs/Build_Decode_BP/scripts/modules/guessthebuild/GuessTheBuildManager.js — Switches builder/guesser roles and Creative/Adventure state across rounds while relying on the shared inventory cleanup.
Must Preserve
  • Normal role rotation between builder and guesser.
  • Pre-game/lobby inventory restoration policy.
  • Reconnect recovery semantics.
  • Intentional map-owned equipment if any is later introduced.

05MAJORVERIFIED

Players can fly out of their assigned arena during active gameplay

BUG-BAD-PHYSICAL-ARENA-ESCAPE
View Details ↓Collapse Details ↑
Issue
During the playing phase, every participant is granted mayfly=true. The selected artifact has no position-boundary enforcement for active players, and voxel-path analysis from both builder and guesser spawns finds a continuous two-block-high air path beyond the authored arena loading bounds in all four arenas. A player can therefore leave the physical arena while the session still treats them as a member of the original arena.
How to Reproduce
  1. Start any Build & Decode arena and reach the active playing phase.
  2. As either builder or guesser, use the granted flight ability.
  3. Fly toward the open side/top of the gameplay structure until crossing outside the arena loading bounds.
  4. Confirm the player remains a member of the original match and is not teleported back or removed for leaving the physical arena.
Observed
Builder and guesser roles receive mayfly during playing, while the service only removes a player for dimension change, not for leaving arena bounds. Static voxel traversal reaches outside the loading envelope from both role spawns in Arena 1-4.
Expected
Players remain physically contained within the gameplay space owned by their assigned arena, or any allowed flight/movement outside that space is detected and reconciled before it can expose another arena or invalidate isolation.
Resolution
Either remove flight from roles that do not require it, physically contain the gameplay volume, or add one canonical arena-position enforcement owner that returns/departs players leaving their assigned arena. Preserve existing role movement that is intentionally required inside the build/guess space.
Technical Analysis
GuessTheBuildManager.activateRound() grants mayfly=true to every online participant, and ArenaSessions.applyRole() does the same for reconnecting players while playing. ArenaService's active-session scan only reacts to missing players or dimension changes; there is no arena-position containment owner. Direct Bedrock LevelDB voxel analysis found a continuous two-block-high air path from builder and guesser spawns to coordinates outside the authored loading bounds for Arena 1, and the gameplay/loading volumes of Arenas 2-4 are voxel-equivalent to Arena 1, reproducing the same escape path.
Source Context
behavior_packs/Build_Decode_BP/scripts/modules/guessthebuild/GuessTheBuildManager.js — activateRound() gives every participant mayfly=true during playing.
behavior_packs/Build_Decode_BP/scripts/modules/arena/ArenaSessions.js — Reconnect role application restores mayfly=true while playing.
behavior_packs/Build_Decode_BP/scripts/modules/arena/ArenaService.js — Active-session lifecycle checks missing players and dimension changes but does not enforce arena position bounds.
Must Preserve
  • Arena-scoped membership and scoring.
  • Builder access to the authored plot.
  • Guesser viewing/interaction flow.
  • Four-arena logical isolation and reconnect recovery.

06MAJORVERIFIED

Time bonus thresholds do not match the authored scoring table

BUG-BAD-TIME-BONUS-SCORING
View Details ↓Collapse Details ↑
Issue
Correct guesses receive the wrong time bonus for several elapsed-time ranges. The authored scoring table defines 8/10/15/25/30/50-second thresholds, while the scoring function checks 5/10/15/20/30 and never checks 8, 25, or 50.
How to Reproduce
  1. Start a normal Build & Decode match and reach an active guessing round.
  2. Make a correct guess within 8 seconds and compare the awarded time bonus with the Points.timebonus table.
  3. Repeat with a correct guess at 16-25 seconds and at 31-50 seconds.
  4. Confirm the effective bonuses are +5, +2, and 0 instead of +10, +3, and +1.
Observed
The scoring function gives +5 instead of +10 through 8s, +2 instead of +3 from 16-25s, and 0 instead of +1 from 31-50s. These points feed player/team scores and can change standings and persisted leaderboard results.
Expected
Time bonuses follow the selected artifact's Points.timebonus table: +10 through 8s, +5 through 10s, +4 through 15s, +3 through 25s, +2 through 30s, +1 through 50s, then 0.
Resolution
Use the canonical thresholds from Points.timebonus (or derive/sort the numeric keys) instead of maintaining a second hard-coded threshold list.
Technical Analysis
GuessTheBuildData.js defines the authored timebonus thresholds as 8, 10, 15, 25, 30, and 50 seconds. GuessRules.getTimeBonus() instead iterates [5, 10, 15, 20, 30]. Missing keys are skipped, so the next lower configured reward or default is returned. The defect is deterministic from source and does not require runtime proof.
Source Context
behavior_packs/Build_Decode_BP/scripts/modules/guessthebuild/GuessTheBuildData.js — Lines 17-24 define the authored time-bonus thresholds and reward values.
behavior_packs/Build_Decode_BP/scripts/modules/guessthebuild/GuessRules.js — Lines 103-110 use a different threshold list when calculating the bonus.
behavior_packs/Build_Decode_BP/scripts/modules/guessthebuild/GuessTheBuildManager.js — The returned time bonus is added directly to correct-guess points and persisted into player/team scoring.
Must Preserve
  • Existing first/second/third/other guesser base points.
  • Builder contribution scoring.
  • Team and individual score conservation.
  • Persisted match/leaderboard result semantics.

07MINORVERIFIED

Guess action temporarily disables Exit to Lobby

BUG-BAD-GUESS-EXIT-COOLDOWN
View Details ↓Collapse Details ↑
Issue
The Guess item and Exit to Lobby item share the same minecraft:cooldown category and both use a two-second cooldown. Bedrock applies cooldowns by category, so using Guess also places Exit on cooldown even though leaving the match is a separate control.
How to Reproduce
  1. Enter an active guessing phase with both Guess and Exit to Lobby items available.
  2. Use the Guess item.
  3. Immediately switch to Exit to Lobby and attempt to use it within two seconds.
  4. Confirm Exit remains on the shared cooldown instead of being independently usable.
Observed
Both builddecode:guess and builddecode:exit_game use cooldown category wind_charge for two seconds, so activating one temporarily cools down the other.
Expected
Guess anti-spam cooldown should not disable the player's independent Exit to Lobby control.
Resolution
Give Guess and Exit distinct map-owned cooldown categories (for example builddecode_guess and builddecode_exit), or remove the Exit cooldown if it has no independent need. Do not share a generic vanilla category across unrelated controls.
Technical Analysis
The item definitions independently assign the same minecraft:cooldown category, wind_charge, to Guess, Exit to Lobby, and the lobby selector item. Bedrock cooldown semantics apply to every item sharing a category. This is a deterministic cross-item configuration collision rather than a form/UI timing issue.
Source Context
behavior_packs/Build_Decode_BP/items/guess.json — Defines minecraft:cooldown category wind_charge with duration 2.
behavior_packs/Build_Decode_BP/items/exit_game.json — Defines the same minecraft:cooldown category wind_charge with duration 2.
behavior_packs/Build_Decode_BP/items/lobby.json — Also reuses wind_charge, confirming the category is not scoped to Guess.
Must Preserve
  • Guess anti-spam protection.
  • Exit confirmation flow.
  • Lobby navigation behavior.

BUG-BAD-DEBUG-STICK
View Details ↓Collapse Details ↑
Issue
A normal builder can hold a stick and trigger production debug tooling, cancelling block interaction and exposing coordinate JSON unrelated to gameplay.
How to Reproduce
  1. Enter a Build & Decode building phase as the active Creative builder.
  2. Obtain and hold a normal Minecraft stick.
  3. Interact with a block.
  4. Confirm normal interaction is cancelled and coordinate/debug output is shown.
Observed
Any builder holding a normal stick can trigger the imported coordinate picker without an admin requirement.
Expected
Temporary coordinate tooling is removed from production or restricted to developer/admin users.
Resolution
Remove the debug-stick import from production or gate the existing tool behind the current developer/admin permission owner.
Technical Analysis
Production main.js imports the temporary debug-stick module. That module subscribes directly to block interaction, explicitly requires no admin tag, and the arena interaction guard lets stick interactions pass through.
Source Context
behavior_packs/Build_Decode_BP/scripts/main.js — Imports the temporary debug-stick module into the production entry point.
behavior_packs/Build_Decode_BP/scripts/dev/debug-stick.js — Implements the non-admin stick coordinate picker and debug output.
Must Preserve
  • Normal gameplay stick behavior must remain available when the developer tool is disabled.
