01MAJORVERIFIED

Reconnect during preload can bypass the fresh-session inventory wipe

BUG-ATK-PRELOAD-INVENTORY
View Details ↓Collapse Details ↑
Issue
A player can disconnect before the preload wipe and reconnect after it, carrying ordinary stale items into the new Attack session.
How to Reproduce
  1. Carry a recognizable ordinary item before starting an Attack match.
  2. Disconnect before the preload inventory-clear callback runs.
  3. Reconnect after that callback while the session is still preloading.
  4. Confirm the stale item remains when the match reaches the initial buy phase.
Observed
The wipe only targets players online at the preload callback, while reconnect and the first buy-phase loadout do not remove ordinary stale items.
Expected
Every participant entering a fresh Attack session receives the same full inventory reset regardless of reconnect timing.
Resolution
Track the fresh-session inventory reset per player and replay the full clear on reconnect before preload or buy-phase continuation.
Technical Analysis
Attack performs its full wipe only over players online when preload reaches the clear callback. The preloading reconnect path does not replay that boundary, and the initial buy-phase loadout uses partial managed-item cleanup rather than a full inventory clear.
Source Context
behavior_packs/BP/scripts/chunks/chunk-Y6V6JTGX.js — Owns Attack preload clearing, reconnect recovery, and loadout cleanup behavior.
Must Preserve
  • Normal kit-managed item cleanup must retain its current mid-session behavior.

02MAJORVERIFIED

Reconnect bypasses an active combat respawn countdown

BUG-ATK-RESPAWN-RECONNECT
View Details ↓Collapse Details ↑
Issue
A player can disconnect during the death countdown and reconnect back into active Attack gameplay before the intended respawn delay finishes.
How to Reproduce
  1. Start an Attack match and die during active combat.
  2. Disconnect while the respawn countdown is running.
  3. Reconnect before the countdown expires.
  4. Confirm the player returns to active gameplay before the original countdown finishes.
Observed
CombatTracker restores the countdown, then GameManager restores survival, loadout, and gameplay position about five ticks later.
Expected
A reconnecting player with a pending respawn stays in spectator/death state until the existing countdown ends.
Resolution
Make GameManager defer to the existing pending-respawn owner before restoring survival, loadout, or gameplay position.
Technical Analysis
CombatTracker correctly owns pending respawns and restores spectator state on reconnect. GameManager independently restores active-session state shortly afterward without checking that pending respawn, overwriting the correct death lifecycle.
Source Context
behavior_packs/BP/scripts/chunks/chunk-Y6V6JTGX.js — Contains pending respawn ownership and active-session reconnect recovery.
Must Preserve
  • Normal reconnect outside a pending respawn must continue restoring the active session.

01MAJORVERIFIED

Six playable arenas expose only two concurrent sessions

DM-ATK-ARENA-CAPACITY
View Details ↓Collapse Details ↑
Issue
Attack presents six playable arena surfaces, but only two can run at once; additional ready groups must queue despite having their own arena.
How to Reproduce
  1. Prepare valid parties in 3 different Attack arenas.
  2. Start the first 2 arenas so both hold active arena leases.
  3. Ready and start the third arena.
  4. Confirm the third group is queued even though its own visible arena is otherwise available.
Observed
Six arenas accept parties, but MAX_CONCURRENT_ARENAS limits active ticking-area leases to two and queues the third session.
Expected
Presented independent arena capacity matches delivered concurrency, or the lower limit is explicitly authored as the player-facing capability.
Resolution
Reduce per-arena residency cost or use another proven simulation strategy so visible arena capacity can run concurrently; keep queueing as overflow handling.
Technical Analysis
The selected artifact exposes six independent arena/join surfaces while runtime admission hard-caps arena ticking leases at two. The queue is a mitigation path, not evidence that the six visible arenas were authored to mean only two concurrent sessions.
Source Context
behavior_packs/BP/scripts/chunks/chunk-Y6V6JTGX.js — Defines the six Attack arena surfaces, MAX_CONCURRENT_ARENAS, ticking-area lease admission, and queue feedback.
Must Preserve
  • Arena isolation and existing queue feedback must remain intact.
