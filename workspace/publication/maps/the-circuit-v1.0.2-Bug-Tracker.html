01MAJORVERIFIED

Disconnecting while carrying the enemy flag does not return it to base

BUG-CIR-CAPTURE-FLAG-DISCONNECT
View Details ↓Collapse Details ↑
Issue
A Capture Run player can disconnect while carrying the enemy flag and leave the arena state believing the flag is still carried, while the visible rider can disappear.
How to Reproduce
  1. Start Station 5 / Capture Run.
  2. Pick up the enemy flag.
  3. Disconnect before returning it to the home flag.
  4. Reconnect or inspect the arena state.
  5. Confirm the enemy flag has not returned to base and the carrier visual/state is inconsistent.
Observed
Manual runtime testing reproduced the stale carrier state. Source has no Capture Run playerLeave handler, keeps carrierPlayerId while the player is offline, and _ensureFlags intentionally refuses to respawn the enemy flag while carrierPlayerId is set.
Expected
If the carrier disconnects, the carried flag is detached and the enemy flag returns to its original base immediately or through a deterministic reconnect-safe reset.
Resolution
Add a Capture Run playerLeave path that atomically clears carrier ownership, removes/despawns the rider flag, and respawns the enemy flag at its configured base before saving state.
Technical Analysis
CaptureRunRoundService subscribes to playerSpawn but not playerLeave. _ensureFlags skips enemy-flag spawning whenever carrierPlayerId is non-null. No disconnect path calls _clearCarrier(), so carrier ownership can remain stale across the offline interval. This differs from Attack/Composite flag services, which explicitly invoke handleCarrierDeath on playerLeave.
Source Context
behavior_packs/BP/scripts/chunks/chunk-M57C5SP4.js — CaptureRunRoundService keeps carrierPlayerId across disconnect and suppresses enemy flag respawn while that id is set; no playerLeave cleanup exists.
Must Preserve
  • Normal death/retry flag reset, active-session reload recovery, and successful capture scoring.

02MAJORVERIFIED

Disconnect during a gameplay cinematic can advance the round while the player is offline

BUG-CIR-CINEMATIC-DISCONNECT-ADVANCE
View Details ↓Collapse Details ↑
Issue
Circuit gameplay cinematics keep counting down after the assigned player disconnects. When the cinematic expires, the round-start event is emitted even though the player is still offline.
How to Reproduce
  1. Reach a gameplay transition cinematic, reproduced on Stations 2 and 3.
  2. Disconnect while the cinematic is still running.
  3. Remain offline long enough for the cinematic timer to expire.
  4. Reconnect after the round has advanced.
  5. Observe the resumed NPC wave/path state; in the reproduced case attacking NPCs no longer break blocking blocks correctly.
Observed
Manual testing on Stations 2/3 found that disconnecting during the cutscene could leave attacking NPCs unable to break blocks after reconnect. Source confirms GameplayCinematicService._tick advances states without requiring the player to be online, _completePlayer emits GAMEPLAY_CINEMATIC_COMPLETE, and SessionStartService starts the round unconditionally from that event.
Expected
A gameplay transition should pause/defer completion while its assigned player is offline, then resume/rebind the round cleanly after reconnect.
Resolution
Do not complete a player's gameplay cinematic while that player is offline. Preserve the remaining cinematic stage, resume it on initialSpawn, and only emit GAMEPLAY_CINEMATIC_COMPLETE after the player is present and transition preparation is valid. Reinitialize/verify NPC path-obstruction state when resuming.
Technical Analysis
The generic cinematic lifecycle has no offline pause condition. _enterStage simply returns when the player object is absent, but _tick continues decrementing stageRemainingTicks and eventually calls _completePlayer(). The completion event then starts Last Stand/Fortify/other round services even with no online player. This creates a real offline-start lifecycle window consistent with the tester's Stations 2/3 path-breaking failure. The generic lifecycle defect is source-proven; the exact downstream NPC-state corruption should be regression-tested across all five Circuit stations.
Source Context
behavior_packs/BP/scripts/chunks/chunk-M57C5SP4.js — GameplayCinematicService advances and completes offline states; SessionStartService starts the target RoundService directly from the cinematic-complete event.
Must Preserve
  • Normal reload recovery, per-player independent sessions, cinematic persistence, and existing round handoff timing when the player stays online.

03MAJORVERIFIED

Station 4 can inherit stale items from the previous Fortify round

BUG-CIR-ST4-CHEST-RESET
View Details ↓Collapse Details ↑
Issue
The Loadout Trial economy station can begin with leftover items in the base/resource chest from Station 3, allowing non-economy resources to survive into a round that is supposed to rely on the coin budget.
How to Reproduce
  1. Complete Station 3 / Fortify through its final tier while leaving building resources in the resource chest.
  2. Continue normally into Station 4 / Loadout Trial.
  3. Open the base/resource chest before spending the Loadout Trial budget.
  4. Confirm items from Station 3 remain instead of the chest starting empty.
Observed
Manual runtime testing found items from the final Fortify tier still present in the Station 4 base chest. The selected source explicitly includes the Fortify resource chest in Loadout Trial's reset-chest list and calls the clear path during preview, so the delivered runtime state contradicts the intended reset path.
Expected
Every Loadout Trial tier starts with the configured reset chests empty except for state intentionally granted by the Loadout Trial economy system.
Resolution
Make the Fortify → Loadout Trial handoff perform and verify a deterministic container reset after world/pathway preparation and before the player receives the Station 4 economy budget. Treat all configured reset chests as a fresh-session invariant.
Technical Analysis
Loadout Trial defines reset chest (1,-48,-135), the same location used by the Fortify resource chest, and _beginPreview calls _clearResetChests(). Because the runtime test still retains prior-station items, the reset path is not reliably taking effect across the Fortify → Loadout Trial handoff. The bug is proven by runtime behavior; the precise timing/ownership failure should be fixed without weakening the reset contract.
Source Context
behavior_packs/BP/scripts/chunks/chunk-M57C5SP4.js — Fortify resource chest is cleared during Fortify cleanup; Loadout Trial reset list includes the same chest and _beginPreview invokes _clearResetChests().
Must Preserve
  • Loadout Trial coin budget, shops, intended kit/loadout state, and Fortify cleanup behavior.

04MAJORVERIFIED

Fortify leaves a spruce gate that Loadout Trial enemies cannot break

BUG-CIR-ST4-SPRUCE-GATE
View Details ↓Collapse Details ↑
Issue
After Station 3, the shared gate is restored as spruce wood. Station 4 / Loadout Trial does not reopen that gate, while its NPC path-breaking rules do not support spruce wood, leaving an unintended barricade in the attack route.
How to Reproduce
  1. Complete Station 3 / Fortify and continue through the normal handoff to Station 4.
  2. Start Loadout Trial Tier 2.
  3. Observe the shared route/gate area that Fortify restores.
  4. Confirm a spruce-wood barricade remains and attacking NPCs cannot break it.
Observed
Manual runtime testing found the Station 4 Tier 2 barricade could not be destroyed. Source confirms Fortify cleanup restores the shared gate to spruce_wood, Loadout Trial preparation does not call the shared gate-open routine, and the NPC break rules only support wool/glass, oak planks, and terracotta.
Expected
Loadout Trial starts with its authored route open, with no leftover Fortify gate blocking the wave.
Resolution
Open/clear the shared Fortify gate during Loadout Trial preparation before the round starts, matching the explicit Capture Run handoff behavior. Do not add spruce wood to the break allowlist unless spruce is intentionally part of gameplay.
Technical Analysis
Capture Run explicitly calls FortifyBuildService.ensureGateOpen() because Fortify cleanup restores the shared gate to spruce wood. LoadoutTrialRoundService.prepare() lacks the equivalent call. LastStandPathObstructionService marks spruce_wood unsupported because its break-rule sets only include wool/glass, oak_planks, and terracotta. The handoff therefore creates an unreachable break condition for the NPC wave.
Source Context
behavior_packs/BP/scripts/chunks/chunk-M57C5SP4.js — Fortify cleanup restores the gate with spruce_wood; Loadout Trial prepare omits ensureGateOpen(); NPC break rules reject spruce_wood as unsupported.
Must Preserve
  • Fortify should still restore its authored gate when leaving the Building round; Capture Run gate-opening behavior must remain intact.

05MINORVERIFIED

Normal gameplay resources expose the production DebugStick

DM-CIR-DEBUG-STICK
View Details ↓Collapse Details ↑
Issue
Ordinary Circuit players can craft a stick from normal gameplay planks and trigger production coordinate-debug output without developer permission.
How to Reproduce
  1. Start a Circuit round that grants the normal block resources.
  2. Use 2 supplied oak planks to craft sticks.
  3. Hold or use a stick as a normal non-developer player.
  4. Confirm DebugStick coordinate-selection output appears.
Observed
DebugStickService is initialized in release and handles normal sticks; Circuit supplies oak planks in Survival, making the trigger craftable.
Expected
Production debug interactions are disabled for ordinary players or gated by the existing developer permission owner.
Resolution
Remove DebugStick from the release bootstrap or gate its stick interaction through the existing developer permission owner. If Circuit is intentionally non-crafting during managed stations, enforce that gameplay policy at the crafting/UI layer as an additional hardening measure.
Technical Analysis
The production bootstrap initializes DebugStickService and its item-use path has no developer/admin gate. Circuit supplies oak planks as starting/shop resources and active gameplay uses Survival, so vanilla crafting closes the trigger reachability path.
Source Context
selected Circuit behavior-pack gameplay bundle — Contains production DebugStick initialization, stick item-use handling, normal plank grants/shop resources, and Survival gameplay mode.
Must Preserve
  • Legitimate gameplay resources and intended shop/loadout behavior must remain available; do not rely on crafting restriction alone to protect developer-only controls.
