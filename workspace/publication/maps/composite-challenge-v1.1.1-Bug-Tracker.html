01BLOCKERVERIFIED

Arena can restart while its asynchronous world reset is still running

BUG-CMP-ASYNC-RESET
View Details ↓Collapse Details ↑
Issue
The arena is marked idle before its multi-tick world reset finishes, so a new session can start while old reset work is still changing the map.
How to Reproduce
  1. Run a Composite arena and change blocks covered by the arena reset.
  2. End or reset the match.
  3. Start the same arena again before reset processing finishes.
  4. Confirm blocks can continue changing underneath the new session during setup or gameplay.
Observed
resetGame starts reset work without awaiting it, then publishes idle state while the reset continues over later ticks.
Expected
The arena remains unavailable until its reset finishes, or start admission is blocked by the existing reset lock.
Resolution
Keep the arena unavailable until the existing reset Promise settles, or include the existing reset-in-progress lock in canonical start admission.
Technical Analysis
ResetMapService performs a chunked multi-tick reset, but resetGame discards its Promise and saves the default idle session immediately. Start validation does not consult ResetMapService's reset-in-progress state, so the same arena can be admitted again before mutation ends.
Source Context
chunk-2GRFUQFH.js — Contains ResetMapService, resetGame, idle publication, and start admission logic.
Must Preserve
  • Arena resets must remain bounded and non-blocking across ticks.
  • One arena reset must not block unrelated arenas.

02BLOCKERVERIFIED

Arena-specific ticking areas are declared but never created

BUG-CMP-TICKING-AREAS
View Details ↓Collapse Details ↑
Issue
Started arenas never create their declared simulation regions, so distant spawning, pathing, and wave progression depend on player-loaded chunks.
How to Reproduce
  1. Start a Composite Challenge arena and progress to gameplay that spawns or moves entities far from players.
  2. Keep players away from the remote spawn or pathing region.
  3. Continue until the game depends on that distant simulation region.
  4. Confirm remote spawning, pathing, or wave progression can stop because the arena region is not kept ticking.
Observed
Only lobby and permission ticking areas are created; the configured per-arena ticking areas are never materialized.
Expected
Each started arena activates its required simulation regions before gameplay depends on remote chunks.
Resolution
Create and release the selected arena's declared simulation regions through the existing residency owner before gameplay uses remote chunks.
Technical Analysis
Arena configuration defines and offsets per-arena ticking regions, but the only runtime tickingarea-add owner consumes WorldData entries for lobby and permission. No second creation path or persisted arena ticking-area names were found in the selected artifact.
Source Context
chunk-WYD2CS7M.js — Declares and offsets the per-arena ticking-area configuration.
chunk-KPA6ZKUE.js — Contains the only runtime tickingarea-add owner and only applies lobby/permission regions.
Must Preserve
  • Lobby and permission ticking areas must keep their existing lifecycle.

03MAJORVERIFIED

Cleanup in one arena can invalidate another arena's flag carrier

BUG-CMP-CROSS-ARENA-FLAG
View Details ↓Collapse Details ↑
Issue
Ending or resetting one Composite arena can remove another arena's active carrier marker, causing its flag objective to drop or reset unexpectedly.
How to Reproduce
  1. Run Composite Attack concurrently in Arena A and Arena B.
  2. In Arena B, take the red flag and remain alive as its active carrier.
  3. Complete, retry, or reset Arena A so its flag cleanup runs.
  4. Confirm Arena B drops or returns its flag even though its carrier did not die or disconnect.
Observed
Flag cleanup receives one arena ID but removes the shared carrier tag from every online player in the world.
Expected
Per-arena cleanup changes only the flag carrier state owned by that arena.
Resolution
Scope carrier-tag cleanup to the carrier owned by the target arena, or make the carrier tag arena-specific while keeping flagStates as the authority.
Technical Analysis
Carrier identity is split between arena-local flagStates and the global ctf_composite_attack_flag_carrier tag. FlagService.cleanup(arenaId) removes that tag from all world players, so Arena A cleanup invalidates Arena B's otherwise-valid carrier.
Source Context
chunk-2GRFUQFH.js — Contains Composite Attack flag state, shared carrier tag validation, per-arena transitions, and world-wide cleanup.
Must Preserve
  • Flag death/disconnect recovery must remain per-arena.

04MAJORVERIFIED

Reconnect during preload can carry stale inventory into a fresh session

BUG-CMP-PRELOAD-INVENTORY
View Details ↓Collapse Details ↑
Issue
A player who misses the online-only preload wipe can reconnect and retain ordinary stale items when Composite enters the new session.
How to Reproduce
  1. Carry a recognizable non-session item before starting a Composite arena.
  2. Disconnect before the preload inventory clear runs.
  3. Reconnect after the clear while the session is still preloading.
  4. Confirm the stale item remains when preparation or gameplay begins.
Observed
The preload clear only covers online arena players, and later reconnect plus partial loadout refresh does not replay the missed full wipe.
Expected
Every player entering a fresh Composite session receives the same full inventory reset regardless of reconnect timing.
Resolution
Make the fresh-session inventory reset a per-player invariant and reconcile any missed full clear before reconnecting players continue.
Technical Analysis
The full inventory clear iterates only players online at preload time. Reconnect during preloading restores state and position without clearing inventory, while preparation applies loadouts with clearAllSlots disabled.
Source Context
chunk-2GRFUQFH.js — Owns preload inventory clearing, reconnect handling, and preparation loadout application.
Must Preserve
  • Normal mid-session loadout refresh must retain its existing scoped cleanup behavior.

05MINORVERIFIED

Arena floor maintenance mutates blocks around unrelated players

BUG-CMP-CROSS-ARENA-FLOOR
View Details ↓Collapse Details ↑
Issue
An active Composite arena can convert dirt around lobby or other-arena players because its maintenance command targets every player in the world.
How to Reproduce
  1. Keep Player A outside the active Composite arena while standing near dirt.
  2. Start gameplay in Arena B.
  3. Wait for the periodic floor-maintenance interval.
  4. Confirm dirt around Player A changes to grass path despite Player A not belonging to Arena B.
Observed
Each active arena runs a grass-path fill as @a, so the mutation executes around players outside the arena too.
Expected
Periodic arena floor maintenance affects only players and world space owned by that active arena.
Resolution
Execute floor maintenance only for the canonical online-player set of the active arena instead of global @a.
Technical Analysis
Defense and Attack maintenance loops are entered per active arena, but the fill command executes as global @a. The command therefore escapes arena ownership and mutates nearby world state around unrelated players.
Source Context
chunk-2GRFUQFH.js — Contains the per-arena maintenance loop and global execute as @a fill command.
Must Preserve
  • Existing floor repair around legitimate active-arena players must continue.
