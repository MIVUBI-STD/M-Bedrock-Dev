01MAJORVERIFIED ISSUE

Levels 5–9 can resolve OPPOSITE into a direction that is not active for the level

Dynamic OPPOSITE targeting transforms the previous direction by compass opposite without revalidating the result against the level's active directions.

BUG-DEF-INACTIVE-DIRECTION-OPPOSITE
Test / Details ↓Collapse ↑
WHY THIS IS A BUG

Levels 5–9 explicitly restrict which fronts are active. OPPOSITE is applied after that level-domain selection but its result is not checked against the same active-direction list, so the runtime can use a front that the current level configuration did not enable.

IMPACT

Players can be attacked from South before South is introduced by the level progression. Defensive positioning, block placement, team coverage, and encounter difficulty can therefore differ from the authored Level 5–9 front layout.

TEST IN-GAME
  1. Start Defense Challenge on Level 5, 6, 7, 8, or 9 with the declared active fronts visible for that level.
  2. Reach a wave entry that uses OPPOSITE after the previous dynamic target resolves to North.
  3. Observe which logical spawn route is selected for the OPPOSITE entry.
  4. Confirm whether South is selected even though South is not declared active until Level 10.
EXPECTED

Every resolved spawn direction remains inside the current level's declared direction domain.

TEST RESULT
Drop, paste, or browse screenshotsPNG · JPEG · WebP · max 8 MB each
Technical Details ↓
Observed Behavior / Evidence
Levels 5–6 declare north/east and Levels 7–9 declare north/east/west, but OPPOSITE(north) resolves south; South routes are configured and materialized even though South is not active until Level 10.
Why It Happens / Technical Analysis
The resulting South target is routable; no post-transform domain guard was found.
Relevant Code
  • behavior_packs/BP/scripts/chunks/ctf-defense-5V4T54X5.js — Dynamic target resolution/materialization.
  • behavior_packs/BP/scripts/chunks/chunk-SEN6JQP2.js — Levels 5–9 restricted direction sets and OPPOSITE entries.
Recommended Fix
Validate every transformed direction against levelConfig.directions and choose a deterministic valid fallback when the opposite front is inactive.
Must Preserve
  • Dynamic front-selection semantics
  • South dual-route behavior from Level 10 onward
02MAJORVERIFIED ISSUE

Reload does not faithfully restore deferred wave timing and delayed spawn groups

Persisted session state records launched-wave progress but does not fully persist/reconstruct remaining inter-wave and intra-wave deferred work.

BUG-DEF-RELOAD-DEFERRED-WAVE-TIMELINE
Test / Details ↓Collapse ↑
WHY THIS IS A BUG

A persisted active session must resume the same outstanding encounter work, not merely remember which wave index was last launched. The current recovery state cannot reconstruct remaining delays or delayed sub-groups, so reload changes the encounter that was in progress.

IMPACT

After reload, a pending wave can arrive at the wrong time, and Level 15 can permanently omit the delayed East/West group of six NPCs. This changes combat pressure and can make the resumed run easier or structurally different from the pre-reload run.

TEST IN-GAME
  1. Start a level with a pending delayed wave or delayed spawn group and note the remaining delay.
  2. Reload or recover the persisted Defense session before the pending delay expires.
  3. Observe the timing and composition of the next resumed wave or group.
  4. For Level 15 Wave 3, reload during the 10-second delay before the East/West six-NPC group and confirm whether that delayed group is reconstructed.
EXPECTED

Reload preserves the same pending timing and delayed spawn groups that existed immediately before reload.

TEST RESULT
Drop, paste, or browse screenshotsPNG · JPEG · WebP · max 8 MB each
Technical Details ↓
Observed Behavior / Evidence
Recovery resumes from lastLaunchedWaveIndex without using currentWaveElapsedTicks as remaining-delay authority. Level 15 Wave 3 is marked launched before its +10-second East/West group of six NPCs materializes, so reload in that window can lose the in-memory delayed group.
Why It Happens / Technical Analysis
Wave-index persistence is not sufficient to reconstruct all scheduled work.
Relevant Code
  • behavior_packs/BP/scripts/chunks/ctf-defense-5V4T54X5.js — Persisted-session recovery and WaveScheduler resume.
  • behavior_packs/BP/scripts/chunks/chunk-SEN6JQP2.js — Level 15 delayed final-wave entries.
Recommended Fix
Persist a reconstructable pending-wave timeline including remaining delays for intra-wave delayed groups.
Must Preserve
  • Killed-NPC preservation
  • Exactly-once wave launch
  • Level 15 configured composition

01MAJORVERIFIED ISSUE

Configured captureZone is not the authoritative flag-capture boundary

Arena configuration describes captureZone as hostile flag detection, while FlagService uses it for warning coverage and a separate hard-coded radius for defeat.

DM-DEF-FLAG-CAPTURE-AUTHORITY
Test / Details ↓Collapse ↑
WHY THIS IS A BUG

The arena configuration presents captureZone as the flag-detection boundary, but runtime defeat is decided by a separate hard-coded 1.3 horizontal / 1.5 vertical radius. Two different authorities therefore describe the same objective boundary.

IMPACT

Warning and defeat behavior can be reasoned about from different spatial rules. Designers and developers can tune captureZone without changing the actual defeat trigger, creating misleading configuration and making flag-balance changes unreliable.

TEST IN-GAME
  1. Run a Defense level with a hostile approaching the configured flag captureZone.
  2. Observe the hostile while it is inside the configured captureZone but outside the hard-coded 1.3-block horizontal defeat radius.
  3. Confirm whether warning state and defeat state use different boundaries.
  4. Repeat near the 1.3-block boundary to identify the actual defeat trigger.
EXPECTED

Warning and defeat boundaries have one explicit non-conflicting authority whose naming matches runtime behavior.

TEST RESULT

Technical Details ↓
Observed Behavior / Evidence
captureZone is configured/offset per arena, but actual defeat uses horizontal radius 1.3 and vertical radius 1.5.
Why It Happens / Technical Analysis
This is an internal authority mismatch, not a claim that 1.3 itself is the wrong gameplay value.
Relevant Code
  • behavior_packs/BP/scripts/chunks/chunk-S5QGQQ5V.js — captureZone configuration contract.
  • behavior_packs/BP/scripts/chunks/ctf-defense-5V4T54X5.js — Warning-zone derivation and hard-coded defeat radius.
