01MINORVERIFIED ISSUE

Authored final-standings presentation is not used at match completion

Completed matches provide the result only through the arena chat summary before reset. The v1.1.3 artifact contains a dedicated final-standings ActionForm, but the terminal flow never invokes it and does not emit a winning on-screen title or victory sound. Tester runtime confirms there is no dedicated winning UI after the match.

BUG-BAD-FINAL-RESULT-PRESENTATION
Test / Details ↓Collapse ↑
TEST IN-GAME
  1. Complete a normal Build & Decode match through the final round.
  2. Observe the terminal presentation after the winner is determined.
  3. Check the chat/result text and whether a dedicated winning title or final standings UI appears before the arena resets.
EXPECTED

The authored end-of-match presentation is reachable from the completed-match flow so players receive a clear terminal result before the arena resets and returns them to the lobby.

TEST RESULT
Drop, paste, or browse screenshots
Technical Details ↓
Observed Behavior / Evidence
Tester runtime on v1.1.3 confirms the match ends without a dedicated winning title/final UI. Source proves that ArenaService.finish() calls game.say(game.matchSummary()), so players do receive chat text such as 'Match Finished!' and the winning score/result. GuessTheBuildUI.showFinalStandings() remains implemented but has no production caller; finish() also contains no terminal setTitle() or victory-sound call before resetArena().
Why It Happens / Technical Analysis
The result itself is settled and communicated through chat, so this is not a missing-result-data defect. The mismatch is presentation ownership: the artifact contains an authored final standings surface, but the terminal lifecycle only publishes matchSummary() through chat and then resets. No terminal title/sound path compensates for the disconnected final UI.
Relevant Code
  • behavior_packs/Build_Decode_BP/scripts/modules/guessthebuild/GuessTheBuildUI.js — Defines showFinalStandings() as a dedicated final standings ActionForm.
  • behavior_packs/Build_Decode_BP/scripts/modules/arena/ArenaService.js — finish() settles the result, sends matchSummary() as chat, then calls resetArena() without invoking showFinalStandings().
Recommended Fix
After durable result settlement, route completed matches through one terminal presentation owner before reset. Reuse the settled result to show the authored final standings and/or a clear winner title/sound; do not recalculate winners in the presentation layer.
Must Preserve
  • Exact-once result settlement and leaderboard persistence.
  • Correct team Win/Draw semantics from the canonical result.
  • Automatic cleanup and return to lobby after the presentation window.
02MINORVERIFIED ISSUE

The final round still tells players that another round is coming

After the last playable round ends, the HUD still displays 'Next round in …' even though no next round exists and the match will finish after the countdown.

BUG-BAD-LAST-ROUND-NEXT-ROUND
Test / Details ↓Collapse ↑
TEST IN-GAME
  1. Play through Build & Decode until the last playable round completes.
  2. Observe the HUD immediately after the final round ends.
  3. Check whether it displays 'Next round in …' even though the match ends when that countdown finishes.
EXPECTED

When the completed round is the final playable round, the transition UI communicates match completion instead of promising another round.

TEST RESULT
Drop, paste, or browse screenshots
Technical Details ↓
Observed Behavior / Evidence
Tester runtime on v1.1.3 confirms the final round still shows 'Next round'. Source proves GuessTheBuildManager.endRound() unconditionally enters round_end, sets resultsTicks, and immediately renders 'Next round in …'. The round_end tick repeats the same HUD. Only after that countdown does ArenaService.prepareRound() call selectRound(); when no builder/word remains, selectRound() returns false and finish() ends the match.
Why It Happens / Technical Analysis
The misleading UI is caused by transition ordering. The code publishes a generic next-round countdown before terminal eligibility is resolved. Terminal detection occurs later in prepareRound() through selectRound() === false, so the final round temporarily presents a transition that cannot occur.
Relevant Code
  • behavior_packs/Build_Decode_BP/scripts/modules/guessthebuild/GuessTheBuildManager.js — endRound() and the round_end tick unconditionally render 'Next round in …' for every completed round.
  • behavior_packs/Build_Decode_BP/scripts/modules/arena/ArenaService.js — prepareRound() only determines after the countdown that selectRound() is false and then calls finish().
Recommended Fix
Resolve whether another playable round exists before publishing the round-end transition label. Keep the normal countdown for non-terminal rounds, but use terminal/match-complete messaging for the final round and hand off to the final-result presentation.
Must Preserve
  • Normal between-round countdown timing for non-terminal rounds.
  • Existing round cleanup/preparation ownership.
  • Exact-once terminal result settlement.
